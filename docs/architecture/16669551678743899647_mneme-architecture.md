# mneme architecture

## The principle

Every artifact in the agent pipeline carries forward both its value AND the evidence that justifies it. Downstream consumers condition on the evidence, not just the value, so when a contract is questioned later the conversation starts from recorded reasoning rather than restarting cold.

This generalizes BLF (binary forecasting with multi-trial aggregation and post-hoc calibration) to every artifact type the substrate produces: forecasts, tickets, plans, security findings, type proposals.

## The unit of execution

A **program** is one skill invocation and the directory it produces:

```
programs/<program_id>/
  manifest.json          metadata + lifecycle status + versions
  artifact.json          the typed return value
  trace.jsonl            one line per orchestration call
  sessions/              captured claudecode sessions attributed here
  skills/<child_id>/     loopback child programs (recursive)
```

The directory IS the run. Replay reads it. Audit reads it. Calibration reads it. Programs nest via loopback (Claude inside a session calls back into the substrate, opening a child program); recursion is capped to prevent runaway chains.

## The single-binary stance

mneme-substrate is one Rust binary. Plexus RPC is the **boundary protocol** exposed to outside callers (synapse, MCP, WS); inside the binary, modules compose via normal Rust function calls. Plexus is not the internal calling convention.

This means:

- Skill A calling skill B in-process is a Rust function call, not a JSON round-trip
- Program-lifecycle middleware wraps the *external* dispatch boundary; internal composition is recorded by the substrate's awareness of swarm calls
- Loopback is the only place we cross a serialization boundary internally — when Claude inside a session calls back via MCP, that's a real principal change, and the per-program `respond` tool registry handles it

Synapse and other Plexus clients see a normal Plexus server with rich activations. Skills inside compose without the cost or fragility of internal RPC. Tests exercise the same code paths production uses.

## The composition stack

```
External callers (synapse, MCP, WS)
       │
       ▼  Plexus RPC
┌──────────────────────────────────────────────────────────┐
│ Skill activations                                        │
│   forecast / ticketing / planning / security_review /    │
│   strong_typing                                          │
│       │  (Rust calls, not RPC)                           │
│       ▼                                                  │
│ Orchestration                                            │
│   swarm: trial / aggregate / sequential / race           │
│   respond: structured-output protocol                    │
│       │  (Rust calls)                                    │
│       ▼                                                  │
│ Claude sessions                                          │
│   claudecode (inherited from substrate)                  │
│       ▲                                                  │
│       │ MCP loopback                                     │
│ Substrate runtime                                        │
│   program lifecycle (wraps external dispatch)            │
│   per-program tool registry                              │
│   session attribution                                    │
│   calibration store                                      │
└──────────────────────────────────────────────────────────┘
```

## Swarm

`swarm.trial` forks a parent claudecode session N ways, sends the same prompt to each, collects N typed responses validated against a schema (via the per-program `respond` tool), and returns a `TrialBatch`. `swarm.aggregate` then combines them via one of four rules:

- `LogitShrinkage` — Bayesian shrinkage in logit space toward a prior; the BLF aggregation
- `ConcatEvidence` — per-trial summary join with attribution; the BLF carry-forward statistic in prose form
- `MajorityEnum` — discrete majority vote with deterministic tie-break
- `MaxSeverity` — max along an ordered ladder (security findings)

The Swarm trait makes runtime impls swappable: the production runtime drives claudecode; the test fixture returns pre-loaded responses; the stub returns NotImplemented. Skills don't know the difference.

## Calibration

A shared calibration store at `programs/_calibration/` accumulates `(predicted, actual)` observations from resolved forecasts. Once enough data exists, Platt scaling fits a sigmoid correction `p_calibrated = sigmoid(a · logit(p_raw) + b)` that subsequent calls apply. Below the cold-start threshold, calibration is identity-with-eps shrinkage toward 0.5 — pretending we can fit Platt parameters on three data points is precision theater.

## Schema enforcement

Activation methods declare typed return shapes. The substrate validates structured responses against the schema before they leave the activation; bad responses become typed errors. The `respond` tool that backs structured outputs from inside Claude sessions uses the same validation path — Claude either produces a payload that matches the schema or sees a validation error and retries, up to a bounded number of attempts.

## What this fork adds to upstream substrate

Upstream `plexus-substrate` is a generic Plexus RPC server. mneme-substrate keeps everything upstream provides AND adds the machinery above: program lifecycle, swarm orchestration, respond protocol, calibration store, the five skill activations.

## How skills get the runtime

Each skill activation holds an `Arc<MnemeContext>` — a small bundle of programs root + swarm runtime + version strings. `builder.rs` constructs one context inside the substrate's `Arc::new_cyclic` closure (after `claudecode` is built and parent-injected) and clones the `Arc` into each registered skill. The same context exposes `open_program(...)` so skills don't have to duplicate program-lifecycle plumbing.

The production `SwarmRuntime` is `ClaudeCodeSwarmRuntime`, which holds the same `Arc<ClaudeCode<P>>` the hub serves — so external Plexus calls (synapse → forecast.update) and in-process composition (forecast.update → swarm.trial → claudecode.fork+chat) hit the same Claude sessions. Tests use `DeterministicMockSwarmRuntime` (returns pre-loaded responses) or `StubSwarmRuntime` (returns NotImplemented).
