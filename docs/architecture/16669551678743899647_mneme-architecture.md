# mneme architecture (in mneme-substrate)

*Written 2026-04-26 during the autonomous build session. Companion to the planning + ticket repo at https://github.com/hypermemetic/mneme.*

## What this fork adds to upstream substrate

Upstream `plexus-substrate` is a generic Plexus RPC server that hosts activations (claudecode, arbor, orcha, lattice, bash, etc.). `mneme-substrate` keeps everything upstream provides AND adds machinery for **skill orchestration as a platform service**:

```
┌─────────────────────────────────────────────────────────────┐
│ Upstream substrate (claudecode, arbor, orcha, ... )         │
│   Plexus RPC server, MCP bridge, transports                 │
├─────────────────────────────────────────────────────────────┤
│ mneme additions                                             │
│                                                             │
│  src/mneme/                  ← pure types + math (no I/O)   │
│    program/                  ← lifecycle + filesystem layout│
│    swarm/                    ← orchestration types          │
│      aggregate/              ← logit shrinkage, concat,     │
│                                majority, max-severity       │
│    respond/                  ← structured-output protocol   │
│    calibration/              ← Platt scaling + store        │
│    runtime/                  ← substrate-side glue          │
│      program_runtime         ← lifecycle hooks              │
│      tool_registry           ← per-program loopback tools   │
│      session_attribution     ← session ↔ program map        │
│      swarm_runtime           ← Swarm trait + Stub + Mock    │
│                                                             │
│  src/activations/forecast/   ← BLF binary forecasting       │
│  src/activations/ticketing/  ← TDD ticket writer            │
│  src/activations/planning/   ← epic DAG planner             │

│  src/bin/mneme.rs            ← CLI: inspect, programs list  │
└─────────────────────────────────────────────────────────────┘
```

## The single-binary stance

mneme-substrate is **one Rust binary**. Plexus RPC is the *boundary protocol* exposed to outside callers (synapse, MCP, WS). Inside the binary, modules compose via normal Rust function calls — Plexus is not the internal calling convention.

This matters because:

- Skill A calling skill B in-process is a Rust function call, not a JSON round-trip.
- The substrate's program-lifecycle middleware wraps the *external* dispatch boundary; internal composition is recorded by the substrate's awareness of swarm calls, not by re-entering dispatch.
- Loopback is the only place we cross a serialization boundary internally — when Claude inside a `claudecode` session calls back via MCP, that's a real principal change and the per-program `respond` tool registry handles it.

The benefits: synapse and other Plexus clients see a normal Plexus server with rich activations; skills inside compose without the cost or fragility of internal RPC; testing exercises the same code paths production uses.

## Programs

Every external method call that arrives via Plexus opens a `Program` (a `programs/<uuid>/` directory with manifest, artifact, trace, captured sessions, child program subdirectories). The directory IS the residue of execution: replayable, auditable, calibratable.

Layout:

```
programs/<program_id>/
  manifest.json          required: metadata + lifecycle status + versions
  artifact.json          on success: the typed return value
  error.json             on failure: kind/message/stage
  trace.jsonl            one line per swarm orchestration call
  sessions/<id>.json     captured claudecode sessions attributed here
  skills/<child_id>/     loopback child programs (recursive)
```

Children inherit `substrate_version` and bump `depth`; capped at 8 to refuse runaway recursion.

## Swarm — the orchestration primitive

`swarm.trial` forks a parent claudecode session N ways, sends the same prompt to each, collects N typed responses (validated against a schema via the per-program `respond` tool), and returns a `TrialBatch`. `swarm.aggregate` then combines them via one of four rules:

- `LogitShrinkage` — BLF Bayesian shrinkage toward a prior (binary probabilities)
- `ConcatEvidence` — per-trial summary join with attribution (the BLF carry-forward statistic)
- `MajorityEnum` — discrete majority vote with deterministic tie-break
- `MaxSeverity` — max along an ordered ladder (security findings)

The Swarm trait is in `src/mneme/runtime/swarm_runtime.rs`. Three impls today:

- `StubSwarmRuntime` — returns NotImplemented; the production placeholder until the claudecode wiring lands
- `DeterministicMockSwarmRuntime` — returns pre-loaded responses; used in tests to exercise the full pipeline without claudecode
- *(real impl pending — drives `claudecode.fork` + `chat_async` + `poll`)*

| End-to-end pipeline (program → trial → aggregate → calibrate → artifact) | **Proven.** See `pipeline_e2e_program_trial_aggregate_calibrate_artifact` test in `swarm_runtime.rs`. |
| `mneme` CLI (`inspect`, `programs list`, `programs trace`) | Done. `mneme run` stub returns clear "not implemented". |

## What pre-existing substrate code mneme does NOT touch

- The `claudecode` activation itself (no internal changes; consumed via its public API)
- The Plexus dispatch path (the program-lifecycle middleware will hook in here once strategy is decided)
- The MCP bridge (the per-program tool registry will integrate with it once MNEME-S01 spike confirms the loopback supports schema-constrained tool registration)
- `arbor`, `orcha`, `lattice`, `bash`, `mustache`, `changelog` (untouched)

## Working with mneme during development

Run the CLI against any program directory:

```bash
cargo build --bin mneme
./target/debug/mneme programs list --programs-root ./programs
./target/debug/mneme inspect <program-id>
```

Run the test suite (266 tests):

```bash
cargo test --lib
```

Specifically exercise the e2e pipeline:

```bash
cargo test --lib pipeline_e2e
```
